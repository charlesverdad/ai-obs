Meter

A local-first observability daemon for AI coding agents. Every tool call gets a CPU-time and peak-memory number attached to it, grouped by the project the agent is working in — so when one of eight Claude Code windows starts eating the machine, you know which one, and which command did it.

Status Draft for review Date 12 Aug 2026 Scope Claude Code on macOS first Repo ~/work/ai-obs

01The problem

You run many Claude Code instances at once. Some of them go bad — a test suite that never exits, a dev server left running, a language server that leaks until the machine swaps. Right now the only instrument is Activity Monitor, which shows you a node process at 400% CPU and tells you nothing about which agent, which project, or which command spawned it.

What this has to answer

  • Which agent is hurting me? Rank live sessions by CPU and memory, labelled with the project directory and git branch, not a PID.
  • What did it run? Every tool call — every Bash invocation, every MCP call — with wall time, CPU time, and peak memory of everything it spawned.
  • What leaked? Processes still alive after the tool call that started them returned. This is the single highest-value signal here, and nothing today reports it.
  • What did it cost? Token breakdown by input / output / cache-read / cache-creation, by model, by project.
  • Optionally, per PR. Which branch and pull request the work belonged to.

Non-goals

  • Not a hosted service. Everything stays on the machine; no account, no upload. (A shipper is a later, opt-in add-on.)
  • Not a replacement for ccusage / usage-fyi on the pricing side — token→dollar conversion is a solved problem worth reusing.
  • Not a profiler. We attribute resources to tool calls; we do not tell you which line of your test suite is slow.
  • Not a supervisor, at first. Kill actions are proposed in phase 3 and are always operator-initiated.
Framing

Token accounting is a read the log files problem and is already well served. Resource accounting is a hold a handle on a live process tree problem and is not served at all. This project is mostly the second thing, with the first bolted on so that one screen answers both questions.

02What already exists

I went and checked rather than assumed. Three things already exist that this design should stand on.

Claude Code ships a large OpenTelemetry surface

Enabled with CLAUDE_CODE_ENABLE_TELEMETRY=1 plus exporter env vars. It emits metrics, log-events, and (in beta) traces. The parts that matter here:

The gap that decides the architecture

OTel carries session.id but no working directory and no git branch. The whole point of this tool is grouping by project, so OTel alone cannot be the spine. You would have to set OTEL_RESOURCE_ATTRIBUTES in every project's .claude/settings.json — per-repo config for something that should just work. The session transcripts, by contrast, stamp cwd and gitBranch on every single record.

The transcripts are richer than the metrics

I parsed a real session out of ~/.claude/projects/ (495 project directories on this machine). Every record carries sessionId, cwd, gitBranch, version, timestamp, uuid/parentUuid. Record types seen in one session:

Finding — the optional feature is free

Claude Code already writes pr-link records tying a session to prNumber, prUrl, and prRepository. Per-PR grouping — the part flagged as optional — is a join, not a feature. Combined with gitBranch on every record, PR attribution costs essentially nothing.

Prior art, ours and the community's

  • ~/work/usage-fyi and -internal. The CLI delegates collection to ccusage (pinned at 20.0.4) and normalises the result into a Snapshot via a small UsageAdapter interface. That adapter shape is the right seam to copy: { id, available(), collect(), toSnapshot() }. The token maths and model pricing are worth lifting wholesale; the sharing/rendering half is not relevant here.
  • Community stacks. ColeMurray/claude-code-otel, SigNoz, and the Grafana write-ups all wire the same pipeline: Claude Code → OTel Collector → Prometheus → Grafana. They all stop at tokens, cost, lines-of-code, and session counts. None of them touch process resources.

Build or buy

Buy would mean OTel Collector + Prometheus + Grafana: three long-running services, a scrape config, a dashboard JSON, and still no answer to the actual question, because no exporter knows that PID 44231 belongs to the Claude Code window in ~/work/remin. You would end up writing the process collector anyway, and then feeding it into a stack that is heavier than the thing it monitors.

Recommendation: build, speak OTLP at the edge. One Rust binary, SQLite on disk, its own UI. Ship an optional OTLP exporter so the same data can land in Grafana later, and an optional OTLP receiver so Claude Code's native telemetry can be ingested for cost enrichment. Prometheus and Grafana become integrations, not dependencies.

03What the kernel will actually tell us

The riskiest assumption in this design is that a normal, unprivileged user process can measure other processes accurately enough. I tested it on this machine (macOS 25.5, Apple Silicon) before writing the rest of the doc. Here is what came back.

Enumerate all processes 1.11 ms

827 PIDs with parent links via one sysctl(KERN_PROC_ALL) call. Sampling at 10 Hz costs ~1% of a core.

proc_pid_rusage, same uid rc = 0

Full counters readable for any process owned by the user, including non-descendants. Root-owned PIDs return −1.

Read another process's env blocked

KERN_PROCARGS2 returns argv but strips the environment unprivileged. Rules out one attribution strategy.

Trap — units are not nanoseconds on Apple Silicon

The time fields are mach absolute ticks, not nanoseconds. On this machine mach_timebase_info reports 125 / 3, i.e. a 24 MHz tick. Reading the claude process raw gave 0.901 "seconds" against ps's 36.12 s — the naive reading is 41.67× too low. Every time field must be multiplied by numer/denom. This is exactly the class of bug that ships silently and makes every number wrong but plausible.

Attribution: what does and does not work

Claude Code exports CLAUDE_CODE_SESSION_ID, CLAUDE_PID, CLAUDECODE, and CLAUDE_CODE_ENTRYPOINT into the environment of every process the Bash tool spawns. That inheritance is perfect for attribution — a process 4 levels deep still carries the session ID. The obvious plan is to read those variables from outside.

It does not work unprivileged. I spawned a child and tried to read its environment via KERN_PROCARGS2; the syscall succeeds but the kernel returns argv only. ps -Eww on a same-user process returns 9 bytes. macOS restricts environment reads to root. So:

Why command wrapping is opt-in, not the default

Two reasons. First, your ~/.claude/settings.json already has a PreToolUse Bash hook that rewrites commands — rtk hook claude. Hooks run in parallel, so two hooks both returning updatedInput for the same tool call is an unresolved conflict, and the loser is silently dropped. Second, the Bash tool runs in a persistent shell: wrapping each command in a subprocess breaks cd and export persistence, and mangles pipelines, background jobs, and heredocs. The sampler gets us 95% of the value with none of that blast radius.

What the sampler cannot see

  • Sub-sample-interval processes. A process that lives 40 ms between two 100 ms samples is invisible to the sampler. It is not invisible to the ri_child_* delta, which is why we use both — the delta catches aggregate CPU, the sampler catches identity and memory.
  • Detached grandchildren spawned and orphaned between samples. Rare; mitigated by the sticky PID set and by matching process start-time against open tool spans.
  • Threads. We report per-process, not per-thread. Fine for the stated problem.

04Architecture

One daemon, four inputs, one store. The daemon is the only long-lived process; the CLI and UI are thin clients over the same SQLite file.

Components

The hook endpoint — HTTP, not command

Claude Code supports "type": "http" hooks. This matters more than it looks: a command hook forks a process on every single tool call, in every session. At eight concurrent agents that is a constant drizzle of process spawns — an observability tool that measurably degrades the thing it observes. An HTTP POST to a listener on loopback costs microseconds and no fork. Non-2xx and timeouts are treated as non-blocking errors by Claude Code, so if the daemon is down, your agents keep working and simply go unobserved.

// ~/.claude/settings.json — installed by `meter install`
{
  "hooks": {
    "SessionStart": [{ "hooks": [
      { "type": "command", "command": "meter session-start", "async": true, "timeout": 5 }]}],
    "PreToolUse":   [{ "matcher": "*", "hooks": [
      { "type": "http", "url": "http://127.0.0.1:8770/h/pre",  "timeout": 5 }]}],
    "PostToolUse":  [{ "matcher": "*", "hooks": [
      { "type": "http", "url": "http://127.0.0.1:8770/h/post", "timeout": 5 }]}],
    "PostToolUseFailure": [{ "matcher": "*", "hooks": [
      { "type": "http", "url": "http://127.0.0.1:8770/h/post", "timeout": 5 }]}],
    "SubagentStart": [{ "hooks": [{ "type": "http", "url": "http://127.0.0.1:8770/h/sub" }]}],
    "SubagentStop":  [{ "hooks": [{ "type": "http", "url": "http://127.0.0.1:8770/h/sub" }]}],
    "SessionEnd":    [{ "hooks": [{ "type": "http", "url": "http://127.0.0.1:8770/h/end" }]}]
  }
}

SessionStart is the one exception — a real command hook, run once per session, because it is the only place we can read $CLAUDE_PID from the environment and hand the daemon the root of the process tree. Everything on the hot path is HTTP. Hooks never return a decision, so they can never block or deny a tool call; the endpoint always answers 200 {}.

The sampler

A 10 Hz loop: one KERN_PROC_ALL sysctl (1.11 ms for 827 processes), build the PID→PPID map, mark every descendant of every registered CLAUDE_PID, union with the sticky set of PIDs seen in-tree before, then proc_pid_rusage each tracked PID. Rate adapts: 10 Hz while any tool span is open, 1 Hz when all sessions are idle, and it backs off automatically if its own CPU exceeds a budget (default 2% of one core).

The transcript tailer

Watches ~/.claude/projects/**/*.jsonl with an fsevents watcher plus byte-offset checkpoints, so a restart resumes rather than re-reads. Parses assistant records for the token block, pr-link for PR association, and system/turn_duration for turn timing. This is also the reconciliation path: transcripts are durable, hooks are not, so anything the daemon missed while it was down gets backfilled here.

Storage

Raw samples are never persisted. 10 Hz × ~30 tracked processes × ~100 B is roughly 2.6 GB/day — absurd for a laptop tool. Instead samples live in memory keyed by (tool_span, pid) and collapse to one row per process per tool call when the process exits or the span closes: total CPU, peak footprint, disk bytes, start/end, exit status. Alongside that, a 1 Hz per-session rollup (CPU%, footprint, process count) is written for the "what happened at 3am" timeline. Result: a few MB per active day, in SQLite with WAL so the UI can read while the daemon writes.

05Attribution

Everything hinges on being able to say: this process belongs to this tool call, in this session, in this project. Five joins, each with a stated fallback.

Subagents

Tool events inside a subagent carry agent_id and agent_type, and transcript records carry isSidechain: true. Subagent tool calls are recorded as spans with a parent link, so a project's totals can be broken down main-agent vs. subagent — which matters, since fan-out subagents are a common source of parallel test runs.

06Data model

Six tables. project and session are dimensions; tool_span, proc_stat, session_sample, and llm_usage are facts.

CREATE TABLE project (
  id            INTEGER PRIMARY KEY,
  root          TEXT UNIQUE NOT NULL,   -- git toplevel, else cwd
  name          TEXT NOT NULL,          -- basename, shown in every UI
  repo_remote   TEXT                    -- owner/name, for PR joins
);

CREATE TABLE session (
  id            TEXT PRIMARY KEY,        -- Claude Code sessionId (uuid)
  project_id    INTEGER REFERENCES project(id),
  claude_pid    INTEGER,
  git_branch    TEXT,
  pr_number     INTEGER,                 -- from pr-link records
  pr_url        TEXT,
  cc_version    TEXT,
  entrypoint    TEXT,
  started_at    INTEGER NOT NULL,        -- unix ms throughout
  ended_at      INTEGER,
  end_reason    TEXT
);

CREATE TABLE tool_span (
  id            INTEGER PRIMARY KEY,
  session_id    TEXT REFERENCES session(id),
  tool_use_id   TEXT,
  parent_span   INTEGER REFERENCES tool_span(id),  -- subagent nesting
  agent_id      TEXT, agent_type TEXT,
  tool_name     TEXT NOT NULL,          -- Bash | Edit | mcp__x__y | …
  cmd_digest    TEXT,                    -- normalised command shape, e.g. "just test"
  cmd_full      TEXT,                    -- redacted; off by default
  started_at    INTEGER NOT NULL, ended_at INTEGER,
  ok            INTEGER,
  cpu_ns        INTEGER,                 -- exact: ri_child_* delta on the shell
  cpu_ns_sampled INTEGER,                -- sum over proc_stat, for cross-checking
  peak_footprint INTEGER,                -- max over tracked descendants
  disk_read     INTEGER, disk_write INTEGER,
  proc_count    INTEGER,
  leaked_count  INTEGER                  -- descendants still alive at span close
);

CREATE TABLE proc_stat (          -- one row per process per span, written on close
  id            INTEGER PRIMARY KEY,
  span_id       INTEGER REFERENCES tool_span(id),
  session_id    TEXT REFERENCES session(id),
  pid           INTEGER, ppid INTEGER, depth INTEGER,
  comm          TEXT, argv_head TEXT,
  first_seen    INTEGER, last_seen INTEGER, exited_at INTEGER,
  cpu_user_ns   INTEGER, cpu_sys_ns INTEGER,
  peak_footprint INTEGER,                -- ri_lifetime_max_phys_footprint
  disk_read     INTEGER, disk_write INTEGER,
  instructions  INTEGER, cycles INTEGER,
  attribution   TEXT NOT NULL,          -- 'span' | 'session' (ambiguous)
  orphaned      INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE session_sample (     -- 1 Hz rollup, the timeline
  session_id    TEXT, t INTEGER,
  cpu_pct       REAL, footprint INTEGER, proc_count INTEGER,
  PRIMARY KEY (session_id, t)
) WITHOUT ROWID;

CREATE TABLE llm_usage (          -- one row per assistant message
  session_id    TEXT REFERENCES session(id),
  message_uuid  TEXT PRIMARY KEY,
  request_id    TEXT, ts INTEGER,
  model         TEXT, query_source TEXT, is_sidechain INTEGER,
  input_tokens  INTEGER, output_tokens INTEGER,
  cache_read    INTEGER, cache_creation INTEGER,
  cost_usd      REAL,                    -- OTLP if available, else priced locally
  cost_source   TEXT                     -- 'otel' | 'computed'
);

Retention: proc_stat rows for processes under a CPU/memory floor are dropped after 7 days; session_sample downsamples to 1-minute buckets after 24 hours; tool_span and llm_usage are kept indefinitely (they are small). Defaults, all configurable.

Privacy

Commands are stored as a digest by default — argv[0] plus a normalised shape (just test, cargo test …), never the full string with its flags and paths. Full command capture is opt-in per project. Environment variables are never read or stored. Nothing leaves the machine unless an OTLP endpoint is explicitly configured. That is not just a policy choice: with the env-read path blocked by the kernel, the daemon has no mechanism to see secrets even if it wanted to.

07Detection

Data nobody reads is worthless. Four detectors run against live state and raise a finding with the project name, the session, and the offending command.

Findings surface in meter top, on the dashboard, and — opt-in — as a macOS notification. No automatic killing. The tool proposes meter kill <finding-id>, which terminates the process subtree and records that it did. Killing something a coding agent is mid-way through is a good way to corrupt a working tree, and a monitor that does it on a heuristic is worse than no monitor.

Calibration

All four thresholds start as guesses. Phase 1 ships with detection running in log-only mode; the thresholds get set from a week of the operator's own real data before anything raises a notification. A monitor that cries wolf in week one gets uninstalled in week two.

08Tokens, cost, and PRs

Tokens

The transcript tailer reads the usage block off every assistant record: input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens, plus model, service_tier, and speed. Because the record also carries cwd, gitBranch, sessionId, and isSidechain, the grouping the brief asks for — by project — falls out of a single pass with no extra configuration. That is the concrete reason the tailer is the spine and OTLP is the optional enrichment.

Cost

Two sources, and we record which one was used. If the OTLP receiver is enabled, take Claude Code's own cost_usd_micros — authoritative, already priced, handles subscription vs. API. Otherwise compute locally from tokens × a model price table, the same approach ccusage takes and the same one usage-fyi's adapter already depends on. The price table is refreshed on demand and cached; a stale table is reported as stale rather than silently producing wrong dollars.

PRs

Cheaper than expected. pr-link records in the transcript give prNumber, prUrl, and prRepository directly against a sessionId. For sessions with no pr-link record, fall back to branch: every record carries gitBranch, and gh pr list --head <branch> resolves it. A PR view then aggregates every session that touched that branch: total tokens, total cost, total CPU-hours, peak memory, longest tool calls, and any orphans left behind. "This PR cost $14 and 3.2 CPU-hours" is a genuinely new number.

Worth noting

Sessions move between branches mid-flight — the sampled transcript showed gitBranch changing from main to fix/release-ci within one session. Branch must therefore be recorded per record, not per session, and PR attribution must be a many-to-many join. Getting this wrong would silently misattribute cost.

09Surfaces

meter top

The one that earns the project. Live, ranked by whatever is hurting: project name, branch, CPU%, footprint, process count, the currently-running tool call, and a severity stripe. Drill into a row for the live process tree.

Dashboard

Localhost web UI. Project leaderboard by CPU-hours and cost; session timeline with tool spans over CPU and memory bands; the tool-call table sorted by cost or by CPU; findings feed.

meter report

JSON or markdown for a project, session, or PR. Scriptable, and how this data reaches a PR comment or a weekly summary.

meter doctor

Verifies hooks are installed and firing, the daemon is up, the mach timebase conversion matches ps, and sampler overhead is within budget. The self-check that keeps the numbers trustworthy.

The dashboard's default view should answer the opening question in one screen: a leaderboard of live sessions by resource use, labelled by project, with findings at the top. Everything historical is a click away, not the front page.

11Risks and open decisions

Open decisions for you

  1. Name. The doc uses meter / meterd against the repo name ai-obs. Pick one before the first commit — this is the cheapest it will ever be to change.
  2. Sampler floor. 10 Hz while active is my proposal. Higher catches more short processes at more cost; 5 Hz is defensible if overhead measures worse than expected in phase 0.
  3. Command capture. Digest-only by default, full commands opt-in. If you want full commands globally, say so now — it changes the redaction design, not just a flag.
  4. OTLP receiver in phase 2 or phase 4? Turning it on gets authoritative cost immediately, at the price of asking you to set telemetry env vars. Local pricing avoids that but can drift.
  5. Linux. Worth designing the collector trait against cgroup v2 from the start, or leave the abstraction until it's actually needed?
